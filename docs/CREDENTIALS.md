# Operational credential exposure

This procedure covers an operational credential copied into a chat, screenshot, log, workflow output, repository, or other place outside its intended store. Treat it as exposed even when the copy is later deleted or no misuse is visible. Use private incident records without the credential value. [SECURITY.md](../SECURITY.md) covers incoming vulnerability reports; [release signing](RELEASE-SIGNING.md#key-custody) governs publisher-key compromise.

## Contain, revoke, replace, verify

1. Identify the credential, owner, scope, exposure location and first possible exposure time. Stop affected publishing/deployment jobs while containment is in progress. Preserve sanitized evidence and tell the account owner through an approved private channel. Do not paste a token into a diagnostic command or incident record.
2. **Revoke the exposed credential at the issuing provider first.** Removing a GitHub Actions secret, deleting a screenshot or changing a local copy does not revoke the provider credential. If the credential is shared across services, identify every consumer before replacing it; suspend the affected workflow until replacement is ready.
3. Create a distinct replacement with the least required privileges and an expiry where the provider supports it. Install it in its intended store. For repository Actions secrets, use `gh secret set SECRET_NAME` interactively, as required by decision [B86](strategy/DECISION-REGISTER.md), never a literal value on the command line. Replace a saved host identity through the host-approved Windows Credential Manager procedure; never print or export the old value.
4. Verify that the old credential no longer authenticates through the provider's status/revocation view, that the replacement supports the intended action, and that no unexpected releases, images, tags, packages, workflow runs or host changes appeared during the exposure window. Avoid a live publication just to test a replacement; use a read-only check or the next authorized release. A successful new login alone does not prove the old credential was revoked.
5. Record the incident privately: credential identifier without value, provider, scope, exposure and revocation times, replacement location, verification evidence, affected artifacts, and remaining investigation. Put the reusable decision or control change in the decision register as B86 does, without secret material. Reassess token expiry and a safe expiry-check workflow; the npm workflow already checks weekly and currently records an expiry date. Do not promise the same check for other providers until implemented.

## Provider-specific route

| Credential used here | Intended store and authority | Revocation and follow-up |
|---|---|---|
| npm granular publish token (`NPM_TOKEN`) for `create-phpledger` | npm account token, copied to the GitHub Actions repository secret; can publish the allowed npm package | In the issuing npm account's **Access Tokens** page, revoke the token, or use `npm token revoke <token-id>` without putting the token value on the command line. Create a new granular token scoped to that package and a finite expiry; install with `gh secret set NPM_TOKEN`. Review the npm package's versions and provenance, the npm publish workflow runs, and any unexpected publication. [npm token guidance](https://docs.npmjs.com/about-access-tokens/), [npm revoke command](https://docs.npmjs.com/cli/v11/commands/npm-token/). |
| Docker Hub access token (`DOCKERHUB_TOKEN`) and associated account (`DOCKERHUB_USERNAME`) | Docker Hub account token in Actions; can publish to the permitted Hub repository | In the Docker account's **Personal access tokens** settings, delete/revoke the affected token. Issue a distinct scoped token, install with `gh secret set DOCKERHUB_TOKEN`, and review Hub image tags, digests and access activity. Changing the username secret or deleting the repository secret cannot invalidate the old token. [Docker token guidance](https://docs.docker.com/security/access-tokens/personal-access-tokens/). |
| GHCR workflow credential | The release workflow uses GitHub's job-scoped `GITHUB_TOKEN` with package-write permission, rather than a reusable GHCR password | For a suspected active workflow compromise, cancel the affected run and remove untrusted workflow/runner access; its `GITHUB_TOKEN` expires when the job ends or after at most 24 hours. Review GitHub Actions runs and GHCR package versions/digests. If a separate GitHub PAT was used outside this workflow, revoke it in the issuing GitHub account's **Developer settings → Personal access tokens**, then replace the authorized consumer's secret. [GitHub token lifetime](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [PAT management](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens). |
| Hosting identity saved in Windows Credential Manager | Machine-local identity used by the pinned-SSH publishing/hosting tools; may allow host access within its assigned permissions | Revoke or disable the account credential/key at the **hosting provider or server** first, with host owner coordination. Then remove/replace its matching Windows Credential Manager entry and recheck the pinned host key. Review host authentication and deployment logs, release directories and unexpected changes. Deleting the local Credential Manager entry alone does not revoke a server password or SSH key. |
| Offline publisher private key | Owner-held outside the repository and CI; can sign update metadata accepted by installations with the pinned public key | Follow [release signing key custody and rotation](RELEASE-SIGNING.md#key-custody). A compromised signing key needs an independently authenticated operator notice and re-pinning; it cannot be trusted to announce its own replacement. Review signed metadata and releases from the exposure window. |

The exact provider console labels may change. Use the linked provider documentation and verify the final revocation state before marking an incident contained. Do not perform provider revocation, token creation, repository secret changes or host-account changes merely by reading this procedure.
