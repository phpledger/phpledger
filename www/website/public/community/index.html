Built in the open, with people who keep real books

Questions, reviews and contributions all happen in public. The repository, the discussions and the release notes are on GitHub; announcements are mirrored on the project's social channels. Here is where to find each of them, and how to support its next improvements.

Where the conversation happens

Everything runs through the project's GitHub repository, with announcements mirrored on the social channels, so there is one source of truth and several ways to hear about it.

GitHub Discussions

Questions and answers, ideas, show and tell, announcements and accounting review each have their own category. Ask how to record something, propose an idea, or show how you run your books.

Help review PHP Ledger in real workflows

Version 1.3.0 is released, but independent accounting review, independent security review and supervised pilots have not happened yet. If you can help with any of them, the maintainer wants to hear from you, and the work is credited in public.

Accounting reviewers

Review the chart of accounts packages, the journals and the financial reports for accounting correctness. Point out where the treatment of a transaction is wrong or unclear. Findings are tracked in public once they are safe to publish.

Offer an accounting review

Security reviewers

Review authentication, sessions, database access and file handling on your own installation. Report problems privately through the security policy first, so a fix can land before details are public. Credit in the release notes is yours to take or decline.

Offer a security review

Pilot businesses

Run your books through PHP Ledger alongside your current process for an agreed period. The maintainer supports the pilot, and the checkpoints are agreed in writing before it starts. A supervised month-end close is the goal.

Questions about taking part

Where do I ask a question?

GitHub Discussions is the place for questions, ideas and show-and-tell. It is public, so use made-up figures. The maintainer reads every thread, and answers that turn out to be generally useful become documentation.

Should I report a security problem in public?

No. Report it privately through the security policy first, so a fix can land before details are public. Credit in the release notes is yours to take or decline once the fix is out.

Do you accept pull requests?

Yes. Start with the contributing guide, pick a good first issue or open a discussion about a larger change, and send the pull request with a test. Accounting changes need a worked example with figures that can be checked by hand.
