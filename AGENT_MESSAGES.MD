One commit on `fix/orphan-credit-offset` from `master` `baa2939`. **Not merged, not pushed, nothing deployed.** No migration, no schema change, no chart change, no route, no template — so this branch collides with nothing and needs no migration number under B62.

**What changed.** The offset account of a credit note with no original invoice is now constrained by side: **`income` for a customer credit, `expense` for a supplier debit**, the reserved contra groups (`4-900` / `5-900`) being the offered default rather than the only permitted account. A **bank account and any open-item control stay refused outright and no override buys either** — paying the party is a refund and settling a document is an application, each with its own service. An inactive account is refused first. Before this, only a bank and a control were refused, so the owner capital account, the owner's loan account, the sales account and any ordinary expense account all posted: an expense offset grosses the profit and loss account up on both sides, and an equity or loan offset takes the adjustment out of profit altogether (IFRS 15.70-72, IAS 1.32).

**Where.** One guard, `pl_advance_assert_offset_account()` in `open_item_functions.php`, with `pl_advance_offset_contract()` and `pl_advance_offset_override_claimed()` beside it. It is applied by `pl_recognize_unapplied_credit()` as the credit note is entered **and again inside the posting funnel** by `pl_open_item_validate_direct_advance_basis()`, which previously validated line 0 only and never looked at the offset — its own doc comment claimed a rule the code did not apply. A future credit-note screen therefore cannot widen it by posting directly.

**The override (B53).** `allow_other_offset_account` must be a real boolean `true`, `offset_override_reason` must carry the reason, and the actor must be the **owner** — the same shape as every other deliberate exception here. It is recorded on the `pl_open_item_commands` receipt with its actor and time, inside the payload hash that becomes the journal's source reference, and in plain words on the offset journal line. The funnel refuses the flag unless the reason travels with it. Reversing one is the ordinary linked reversal of that journal; nothing is configured and nothing persists. `docs/accounting/ADVANCES-AND-REFUNDS.md` §5 records the four alternatives rejected (unconstrained offset, requiring the reserved code band, a book-level B37 policy, warn-instead-of-refuse) and the closing accountant question 2 is updated to what is now settled and what is still open.

**Tests:** five new tests in `tests/advance_test.php`, asserting on the refusal **messages** as well as the refusals, so the guard cannot be quietly weakened: income accepted and expense/equity/liability refused on the customer side; expense accepted and income/equity refused on the supplier side; bank, receivables control and advances control refused with and without an override, plus the inactive-account refusal; the override accepted with owner, reason and the text on the journal line, and refused for a missing reason, a non-boolean flag, a changed reason under the same request key and an accountant actor; and the funnel's own validator driven directly, with no service in front of it.
